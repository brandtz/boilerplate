# Prompt: Third-Party Integrations Map

## Sequence Position
8.0.1 — Sixth implementation prompt (Rec 5)

## Phase
Implementation

## Objective
Create the integrations context file and template so every external dependency (databases, auth providers, payment processors, CDNs, etc.) is tracked with configuration requirements, failure modes, and cost implications.

## Dependencies
- 7.0.1 (memory system) complete

## Prerequisites
- Prompt 7.0.1 complete

## Context for the Agent
Real SaaS projects depend on external services. The boilerplate has no artifact for tracking these dependencies — their configuration, failure modes, cost models, or auth mechanisms. Agents make architecture decisions without knowing what's available. This file fixes that gap.

## Required Reading
- `agents/context/project-charter.md`
- `agents/standards/prompt-lifecycle-standard.md`
- `agents/standards/handoff-standard.md`
- `docs/boilerplate-upgrade-intake.md` — Recommendation 5 details

## Scope

### E1-S5-T1: Create `agents/templates/integrations-template.md`
Template with a table/structured format per integration:
- Service Name and Purpose
- Tier/Plan
- Configuration (env vars required)
- Auth Mechanism (API key, OAuth, service account)
- SDK/Client Library and Version
- Known Limitations and Failure Modes
- Cost Model (per-request, per-seat, flat rate)
- Fallback/Degradation Strategy

### E1-S5-T2: Create `agents/context/integrations.md`
Copy from template with boilerplate instruction header:
> This file is populated during architecture review. Every external service dependency must be documented here before implementation begins.

### E1-S5-T3: Update intake prompt (01)
Add an integrations interview question to the intake prompt — ask the sponsor what external services they plan to use. Not all will be known at intake; the Solution Architect populates the rest during architecture review.

### Post-implementation
Run `scripts/validate-boilerplate.sh` — must pass.
